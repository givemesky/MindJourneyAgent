这份实验报告为 **MindJourney RAG 规划系统** 的当前表现提供了一个非常客观的“体检报告”。从数据来看，系统虽然具备了基本的规划能力，但在**精准度**和**约束遵循**方面仍有较大的提升空间。

以下是对这份实验结果的详细深度分析及优化建议：

### 1. [实验 A] 全集约束满足率 (CSR) 分析
*   **整体表现**：平均 **75.74%**。这意味着用户提到的必去景点/餐厅，平均每 4 个就有 1 个被系统“弄丢”了。
*   **异常趋势**：通常难度越高 CSR 越低，但你的结果是 **Easy (69.17%) < Standard (78.67%) < Hard (79.38%)**。
    *   **原因分析**：这非常反直觉。可能的原因是：在 Easy 模式下（通常只有 1-2 天），Planner 逻辑或 LLM 可能觉得行程太短，为了“美观”或“顺路”擅自剔除了某些硬约束；而在 Hard 模式下，因为天数多、空位多，系统更容易把所有硬约束塞进去。
    *   **结论**：系统在“简单任务”下表现出较强的**随机性或过度优化**，缺乏对用户指令的“绝对服从”。

### 2. [实验 C] 方案二：兴趣画像契合度分析
*   **整体表现**：平均 **22.17%**，这是目前**最严重的弱点**。
*   **深度解读**：
    *   这意味着系统自发推荐的“赠送景点”中，竟然有 **近 80% 与用户的兴趣标签不符**。
    *   例如：用户明明喜欢 `Nature (自然风光)`，系统却推荐了一堆 `Shopping` 或 `Culture` 的点。
*   **瓶颈定位**：
    *   **RAG 检索权重问题**：`planner.py` 里的 `_find_smart_node` 函数中，`focus == "interest"` 产生的加分可能远小于地理距离（Distance）带来的减分。导致算法为了“路近”，牺牲了“兴趣”。
    *   **LLM 幻觉**：Qwen 在渲染文本时，可能更倾向于写它知识库里常见的“热门景点”，而忽略了数据源中提供的、真正符合兴趣的景点。

### 3. [实验 D] 方案三：消费定制符合率分析
*   **整体表现**：平均 **56.67%**。
*   **各难度表现**：Standard 最高 (70%)，Hard 最低 (45%)。
*   **原因分析**：
    *   **Hard 模式的累积误差**：在 5-7 天的长途行程中，住宿和餐饮的费用累积非常快。如果 Planner 在选点时没有每一天都严格控价，总价很容易超标。
    *   **价格数据缺失**：由于实验 D 只要正则抓不到预算就按不符合处理，较低的符合率可能暗示了 Qwen 在长文本（Hard 模式）中更容易漏掉“总预算预估”这行固定格式的文字。

### 4. 综合诊断结论
目前系统的状态可以概括为：**“能出方案，但不够听话，且缺乏个性化。”**

*   **优点**：系统已经打通了全链路，能够处理复杂的 Hard 模式请求，且 CSR 随难度增加表现稳健。
*   **致命伤**：**画像契合度（Exp C）极低**，这直接否定了“个性化推荐”的核心卖点。
*   **工程隐患**：Easy 模式下的约束丢失率过高。

### 5. 针对性优化建议

#### A. 提升 CSR (针对实验 A)：
*   **Prompt 强化**：在 `planner.py` 的 Prompt 中加入：`“用户指定的硬约束景点（must_visit_attractions）具有最高优先级，必须全部出现在行程中，严禁替换。”`
*   **代码校验**：在 `solve_plan` 结束后，增加一个简单的检测逻辑：如果 `all_attr_pool` 的长度小于硬约束列表，强制重新抽样。

#### B. 拯救兴趣契合度 (针对实验 C - 核心任务)：
*   **大幅调权重**：在 `planner.py` 的 `_find_smart_node` 中，把 `interest` 的奖励分数从目前的几百提高到几千，甚至改为**硬过滤**（如果 focus 是 interest，只在符合类型的点里抽样）。
*   **RAG 注入优化**：在给 Qwen 的数据源中，标注每个景点的类型。例如：`[数据源] 故宫 (类型:文化)`。这样 LLM 在写描述时会有意识地往文化上靠。

#### C. 稳固消费水平 (针对实验 D)：
*   **酒店控价**：在 `solve_plan` 阶段，针对 `Budget` 画像，强制只在价格低于 300 的酒店中检索；针对 `Luxury`，强制过滤掉低价旅馆。
*   **正则鲁棒性**：虽然是实验脚本问题，但建议后端在生成报告时，由程序自动计算一遍总价并强行追加在末尾，而不是完全依赖 LLM 自己算，这样可以保证 100% 抓取。

实验设计：


设计**约束满足率 (CSR)** 实验的核心在于验证系统从“听到用户要求”到“符号化记录”再到“最终路径实现”的**全链路保真度**。

以下是为您设计的实验思路，分为四个阶段：

### 第一阶段：构建“约束测试集” (Test Suite)
你需要预先设计 20-30 个不同的测试用例（Test Cases），每个用例包含一组不同维度的“硬约束指标”。

1.  **约束的分级定义**：
    *   **基础约束**：目标城市、游玩天数、出行人数。
    *   **实体约束**：指定必去景点（如：中山陵）、指定必吃餐厅或菜系（如：盐水鸭）。
    *   **数值约束**：总预算上限（如：不超过 3000 元）。
2.  **测试用例多样性**：
    *   **简单模式**：3 个约束（城市、天数、人数）。
    *   **标准模式**：5 个约束（基础 + 1个景点 + 1个菜系）。
    *   **挑战模式**：7 个及以上（增加预算上限、特定酒店要求等）。

### 第二阶段：实验执行流程 (Execution Protocol)
为了模拟真实使用场景，你需要一个标准化的操作流程：

1.  **输入模拟**：
    *   可以通过脚本自动读取测试用例，模拟用户分 2-3 轮话术将所有约束抛给 `/v1/plan` 接口。
    *   *注意*：测试时应记录在第几轮对话后，DPI 系统准确识别出了这些约束。
2.  **勾选策略（模拟阶段 C）**：
    *   **全选策略**：在阶段 B 推荐出的卡片中，自动勾选所有符合“测试用例”要求的卡片（例如测试用例要求去“鸡鸣寺”，如果推荐里有，就必须勾选）。
3.  **结果产出**：
    *   触发阶段 D，获取最终生成的 3 套行程方案。

### 第三阶段：校验与评分机制 (Verification & Scoring)
这是实验最关键的部分：如何判断“满足了”？建议采用 **“双重校验法”**。

1.  **关键词匹配（自动化校验）**：
    *   检查 Qwen 生成的文本中是否包含测试用例中的关键词（景点名、人数数字等）。
2.  **逻辑审计（LLM-as-a-Judge）**：
    *   由于 LLM 输出具有随机性，有时它可能写了“前往鸡鸣寺附近的古寺”，虽然没提名字但逻辑是对的。
    *   **思路**：将“原始约束列表”和“生成的行程方案”一起发给一个更强的大模型（如 GPT-4 或另一个 Qwen 实例），让它充当裁判，逐项打勾/打叉。
3.  **预算核验**：
    *   对比系统给出的“预估总预算”是否在用户设定的上限之内。

### 第四阶段：失效分析 (Failure Analysis)
实验不仅仅是算一个分数，更重要的是找出 CSR 为什么不是 100%。你需要对未满足的约束进行归类：

1.  **感知层丢失 (Perception Failure)**：用户说了，但 `constraints_log.json` 里根本没记下来。
2.  **知识图谱缺失 (KG Failure)**：用户要吃某种冷门菜，但数据库（GML）里没有，导致阶段 B 无法推荐。
3.  **执行层幻觉 (Planner Hallucination)**：日志记了，卡片也选了，但 Qwen 在最后渲染排期时把这个景点“忘了”。

构建测试集的目标是**确保覆盖度（Coverage）**和**挑战性（Robustness）**。既然你已经有了明确的维度和10个城市的数据，建议采用“**正交组合 + 业务场景模拟**”的方法来构建。

以下是构建测试集的具体思路：

### 1. 维度全覆盖策略 (Persona Matrix)
首先，计算画像的全部组合：$3 (\text{Consumption}) \times 4 (\text{Interest}) \times 2 (\text{Pace}) = 24$ 种唯一画像。
为了实验的严谨性，你的测试集应确保这 24 种画像在 10 个城市中均匀分布。

*   **设计建议**：每个城市分配 2-3 个核心画像组合，确保总样本量在 25-30 个左右（这是一个既能保证统计意义，又不会让 API 运行太久的平衡点）。

### 2. 约束强度等级划分 (Difficulty Levels)
CSR 测试不仅要看能不能实现，还要看在“极端要求”下能不能实现。建议将测试集分为三个难度：

*   **初级 (Easy)**：1-2个必去景点 + 1个必吃餐厅。天数短（1-2天）。
    *   *验证目的*：系统最基础的直连能力。
*   **中级 (Standard)**：3-5个必去景点 + 2个必吃餐厅。天数中等（3-4天）。
    *   *验证目的*：系统处理多任务和排期的稳定性。
*   **高级 (Hard/Stress)**：6个以上景点 + 3个以上餐厅。天数长（5-7天）或人数多（5人以上）。
    *   *验证目的*：系统的聚类能力（K-means）和长文本渲染的逻辑保真度。

### 3. 基于数据分布的约束选取 (Data-Driven Selection)
不要随机选取景点，要根据你的知识图谱（GML）属性来选：

*   **兴趣对齐测试**：如果画像是 `Nature`，硬约束也选 `自然风光` 类景点。
    *   *看点*：系统是否能顺着用户的意图强化推荐。
*   **兴趣冲突测试（鲁棒性）**：如果画像是 `Nature`，但硬约束强行要求去 `解放碑（Shopping）`。
    *   *看点*：**硬约束是否能成功覆盖（Override）软偏好**。这是 CSR 实验最核心的价值点。

### 4. 典型测试用例场景 (Scenario Design)
你可以模拟以下几种“真实游客”来填充你的 JSON 列表：

1.  **“特种兵大学生”案**：
    *   `Consumption: Budget`, `Pace: Fast`, `Day: 1`, `Attractions: 5+`.
    *   *挑战*：1 天内塞进 5 个点的逻辑合理性和预算控制。
2.  **“中产家庭文化游”案**：
    *   `Consumption: Economy`, `Interest: Culture`, `People: 3-4`, `Day: 3-5`.
    *   *挑战*：多人模式下的房间数计算和餐厅空间容纳（逻辑体现）。
3.  **“奢华享受型”案**：
    *   `Consumption: Luxury`, `Interest: Shopping`, `Pace: Relaxed`.
    *   *挑战*：系统是否跳过了廉价小吃，精准命中了高客单价的餐厅。
